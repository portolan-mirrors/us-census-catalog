A demonstration of cloud-native geospatial

No API.
No server.
Just files.

The Census Atlas maps every US county, tract, block group, ZIP code, place and census block. Nothing serves that data. There is no tile server, no feature service, no database and no API — only static files on object storage, read directly by your browser over HTTPS.

01

Three file formats, and that is the whole stack

Cloud-native geospatial means a format designed so that a client can read part of a file over HTTP, rather than downloading all of it or asking a server to slice it. Everything in this atlas rests on that one idea: an HTTP range request.

PMTiles

What you see on the map

One file per collection holding every vector tile at every zoom, with a directory at the front. MapLibre reads the directory, works out which byte ranges hold the tiles on screen, and asks for exactly those. 52 archives, 18.1 GB — of which a typical map view fetches a few hundred kilobytes.

Replaces: a tile server

GeoParquet

The numbers behind it

Columnar tables with the geometry in them. A query for two columns reads only those two columns, and a bbox column lets a reader skip every row group outside your area. 133 files, 7.7 GB, queryable in place by DuckDB, GeoPandas, QGIS or anything else that speaks Parquet.

Replaces: a feature service and a database

STAC

How anything finds it

A tree of plain JSON describing every collection: its columns, its row count, its extent, its licence, its provenance and the URL of every file. One root document, crawlable by a script, a catalog browser or a language model.

Replaces: a metadata API and a docs site

Why this is worth caring about

  • Nothing to rate-limit you. No key, no quota, no terms of service between you and a public-domain census table.
  • Nothing to go down. A static file has no runtime to crash and no bill to lapse.
  • The data is not trapped behind an interface. Every view in the atlas is reproducible from the files directly — and so is every view the atlas does not offer.
  • It composes. You can join a census table to your own data without either side moving to a shared server.

03

Querying this with an LLM

This catalog is unusually good at being handed to a language model, for a reason that is structural rather than clever: the data describes itself in text, and the data itself is reachable by URL. A model can read the STAC JSON to learn what exists and what the columns mean, then write a query that runs against the files without anything being loaded or provisioned first.

Step 1

Give it the catalog

Paste this into any assistant that can fetch a URL. It is the whole setup — one address, from which everything else is discoverable. 

Read https://data.source.coop/portolan-mirrors/us-census-catalog/catalog.json and the AGENTS.md beside it. It is a STAC catalog of US Census data published as GeoParquet and PMTiles on object storage. Tell me which collections exist and what columns they carry.

AGENTS.md is written for exactly this: a guide at the catalog root, and one in each collection, stating the join keys, the column meanings and the gotchas. Every claim in it is quoted from the Census Bureau or measured from the data.

Step 2

Ask in plain language

Then ask for the answer, not the query. A capable model will pick the right collection, read the column list from the STAC document, write the DuckDB SQL and run it — if it has a tool that can. 

Using that catalog, which 10 counties have the highest share of households with no internet subscription, and what is the median household income in each? Query the GeoParquet directly with DuckDB.

No tool? Ask it to write the query and run it yourself — the SQL in section 04 is the shape it will produce.

Step 3

Keep it honest

The failure mode of an LLM on a dataset is a confident invented column name. Two habits catch it:

  • Tell it to list the columns from the STAC document before writing SQL, and to use only those.
  • Ask for the row count and a few sample rows alongside any aggregate, so a silently empty result is visible.

While writing this page, a draft query used pct_broadband. That column does not exist; the real one is pct_no_internet, and it runs the other way round. Every query on this page was executed against the live files before it was published.

Questions that suit this data

The catalog is strongest on comparison — across places, across scales and across time. Some shapes that work well, each a prompt you can paste:

Ranking & outliers

“Which 20 census tracts in Texas have the highest rent burden, and how does each compare to its county's median?”

One table, one sort. The cheapest kind of question here, and a good first test that your setup works.

Relationships across themes

“Across all counties, what is the correlation between the share of adults with a bachelor's degree and median household income? Which counties are the biggest outliers from that trend?”

Themes live in separate collections, joined on geoid. Income, people, housing, connectivity and wellbeing all share that key at each geography.

Change over time

“Which counties saw median gross rent rise most between the 2015–2019 and 2020–2024 ACS releases, and did their poverty rate move with it?”

The trends collections carry both periods in a period column, plus a chg_ column per indicator so the difference is already computed.

Somewhere specific

“What are the demographics of the census tract containing 40.7128, -74.0060, and how does it differ from the surrounding county?”

Point-in-polygon with ST_Contains, then a prefix of the tract geoid gives you the county. No geocoder needed.

Across scales

“Within Cook County, Illinois, how much does the poverty rate vary between block groups, and which share the most and least internet access?”

The same indicators are published from states down to block groups, and geoid nests: a block group's first five characters are its county.

Joined to your own data

“Here is a CSV of our store locations. For each one, give me the median income and population density of its census tract.”

DuckDB can read your local file and the remote GeoParquet in the same query. Nothing has to be uploaded anywhere.

What this data cannot tell you

Ask an LLM for a causal story and it will happily write one. The data does not support it. Three limits worth putting in your prompt:

  • These are estimates with error bars. Every ACS value has a _moe column beside it (90% margin of error), and some have a _cv. At tract and block-group level the margin is often large enough to swamp the difference you are comparing. Ask for the MOE alongside the estimate.
  • Boundaries move. Tracts were redrawn for 2020, so a 2015–2019 tract is not always the same ground as its 2020–2024 namesake. The trends collections carry a geo_change flag for this; counties and states are far more stable.
  • Correlation across areas is not a fact about people. Two indicators moving together across tracts says nothing about any individual in them.

04

Queries that run

Every example below was executed against the published files, over the public internet, with no credentials. Install DuckDB and paste one in. Each reads only the bytes it needs, so none of them download the whole table.

The highest-income counties in the country

The simplest shape: one remote file, sorted. Returns in a second or two, having read two columns out of a 13 MB table.

INSTALL spatial; LOAD spatial; INSTALL httpfs; LOAD httpfs;

SELECT name, state, median_hh_income, pct_below_poverty
FROM read_parquet('https://data.source.coop/portolan-mirrors/us-census-catalog/counties/county-income/county-income.parquet')
WHERE median_hh_income IS NOT NULL
ORDER BY median_hh_income DESC
LIMIT 5;

Joining two themes on geoid

Income and connectivity are separate collections. geoid joins them — and joins either to any other theme at the same geography.

LOAD spatial; LOAD httpfs;
SET VARIABLE base = 'https://data.source.coop/portolan-mirrors/us-census-catalog';

SELECT i.name, i.median_hh_income AS income, c.pct_no_internet
FROM read_parquet(getvariable('base') || '/counties/county-income/county-income.parquet') i
JOIN read_parquet(getvariable('base') || '/counties/county-connectivity/county-connectivity.parquet') c
  USING (geoid)
WHERE i.median_hh_income IS NOT NULL AND c.pct_no_internet IS NOT NULL
ORDER BY c.pct_no_internet DESC
LIMIT 4;
Result

What changed between the two ACS releases

The trends collections hold both periods. Filter to one period and the chg_ columns give you the movement without a self-join.

LOAD spatial; LOAD httpfs;

SELECT name, period, median_gross_rent, chg_median_gross_rent
FROM read_parquet('https://data.source.coop/portolan-mirrors/us-census-catalog/trends/county-trends/county-trends.parquet')
WHERE period = '2020-2024' AND chg_median_gross_rent IS NOT NULL
ORDER BY chg_median_gross_rent DESC
LIMIT 4;

Which tract contains this point

A spatial predicate against 85,184 tract geometries, straight over HTTPS. No geocoder, no PostGIS, no upload.

LOAD spatial; LOAD httpfs;

SELECT geoid, name, median_hh_income
FROM read_parquet('https://data.source.coop/portolan-mirrors/us-census-catalog/tracts/tract-income/tract-income.parquet')
WHERE ST_Contains(geometry, ST_Point(-122.4862, 37.7694));

Reading only one city's worth of bytes

This is the cloud-native part made visible. The bbox column lets DuckDB skip every row group outside the window, so a national table answers a Manhattan question in about seven seconds without being downloaded.

LOAD spatial; LOAD httpfs;

SELECT count(*) AS tracts_in_bbox
FROM read_parquet('https://data.source.coop/portolan-mirrors/us-census-catalog/tracts/tract-income/tract-income.parquet')
WHERE bbox.xmin > -74.02 AND bbox.xmax < -73.90
  AND bbox.ymin >  40.70 AND bbox.ymax <  40.88;
Result

│ tracts_in_bbox │
├────────────────┤

All 8.2 million census blocks

The blocks collection is partitioned by state, so a two-state question touches two files. A Hive-partitioned glob needs the anonymous S3 endpoint: the HTTPS gateway cannot list a directory, so a glob over it returns 404.

LOAD spatial; LOAD httpfs;
SET s3_region = 'us-west-2';

SELECT state, count(*) AS blocks, sum(pop_total) AS people
FROM read_parquet(
  's3://us-west-2.opendata.source.coop/portolan-mirrors/us-census-catalog/blocks/state_fips=*/*.parquet',
  hive_partitioning = true)
WHERE state_fips IN ('44', '50')
GROUP BY state
ORDER BY state;
Result

Python, if you would rather

GeoPandas reads the same files. So does anything built on Arrow or GDAL — QGIS will open these URLs directly.

import geopandas as gpd

base = "https://data.source.coop/portolan-mirrors/us-census-catalog"
gdf = gpd.read_parquet(f"{base}/counties/county-income/county-income.parquet")
gdf.nlargest(5, "median_hh_income")[["name", "median_hh_income"]]

The join key

geoid is the Census Bureau's GEOID, and it nests by prefix. A block group's first 11 characters are its tract; the first 5 are its county; the first 2 are its state. That is how you roll a tract question up to a county, or push a county question down to block groups, without a crosswalk.

Suffixes on columns

_moe is the 90% margin of error for the estimate beside it. _cv is the coefficient of variation, a quick reliability check: above about 30, treat the estimate as weak. pct_ columns are percentages, not proportions — 4.23 means 4.23%.

Every collection ships a README.md and an AGENTS.md next to its data, listing each column with its source census table. Start from the root AGENTS.md and follow it down.
